# Toreca Vault — X買取相場取得・画像商品識別 確定仕様 v1

- 決定日: 2026-11-13 JST
- 状態: **仕様確定／実装・実データ連携は未完了**
- 対象: 新アプリの**参考買取相場**。実売却額・購入原価・在庫数量とは独立
- 初期監視先: **買取ミミ／カードショップアリウム／トレカショップKURO** のX公式アカウント（正確なアカウントIDは真正性確認後に設定。推測で登録しない）
- 更新方針: 既存スケジューラーの毎日13:45 JSTのmarket-refreshを利用。API等の使用条件・費用と実運用可能性の検証完了後に有効化

## 1. 基本ルール

1. 上記3店の**店舗本人が投稿した買取案内**だけを市場参考データの出典にする。再投稿・第三者の転載・なりすましアカウントは採用しない。店舗名、公式アカウントID、投稿URL・投稿ID、投稿日時、取得日時、改訂・適用期間を保存する。
2. 本文と添付画像の両方から商品情報を抽出する。**本文 → 画像中の文字（OCR） → 商品パッケージの視覚特徴 → 公式商品情報**を統合し、価格と商品を一対一に結びつける。
3. 価格・状態・商品・販売単位のいずれかが未確認・矛盾していれば推測で確定しない。**review** に保存し、必要ならユーザーに確認する。
4. 取得した価格は**買取提示価格（quote）**であり、実際の売却が成立した価格ではない。買取相場の取得によって売却履歴・在庫・購入原価を自動変更しない。
5. 重複投稿、同じ投稿の複数回取得、同一画像の再取得は同一キーで冪等化する。すでに確認された価格を取得エラーで0円や仮値に上書きしない。

## 2. 公式商品マスタ（照合の根拠）

対象商品の公式メーカー／販売元の商品ページまたは公式製品画像を基準とする。商品ごとに次を登録する。

- `productId`（安定ID）、正式名、略称・表記ゆれ、シリーズ・商品型番（判明時）
- **単位**: 単品パック、BOX、カードセット、スターターセット、シングル等
- **公式デザイン参照**: URLと確認日、BOX・パック表面の公式写真、商品ロゴ、主要キャラクター、ベースカラー、特徴的な配置・マーク
- 商品状態の区別: シュリンク有無、テープ有無、未開封・開封済、セット構成、カードの状態・レアリティ
- 公式税込定価（**購入原価の不明時に用いる参考値**。買取相場とは別フィールド）

公式デザイン参照は、利用条件に従ってURLや特徴量を保持する。公式画像の無断再配布や、公開リポジトリへの画像の丸ごと転載を前提としない。

## 3. テキスト・画像の商品同定

### A. 投稿本文・画像内文字
- 商品名・略称、レアリティ／型番、BOX/パック/セット、価格と通貨、買取条件、店舗、更新日時、対象期間を抽出。
- **「買取価格」「強化買取」「買取保証」** と、**販売価格・定価・オリパ価格・希望額・参考価格** を混同しない。
- 1画像に複数の商品の行やカードが並ぶ場合は、**商品と金額を空間的に結びつける**。別商品の横にある金額を誤って割り当てない。
- 数字の `1/箱` `1パック` `9種セット` などの販売単位を確認し、単価か合計かを分離。

### B. 画像の視覚的な識別
- 文字が読みづらい場合も、**公式BOX/パックデザイン、ロゴ、パッケージの色、主要キャラクター、商品形状**を合わせて判定する。
- 類似商品の一例: **30th CELEBRATIONの拡張BOXと9種カードセット** は別`productId`にする。単なる「30th」の文字一致で統合しない。
- 画像は複数候補を比較する。**色やキャラクターだけの単独一致で自動確定しない**。価格札と商品画像が離れている場合もレビュー。
- シングルカードはカード名のほか番号・型番・レアリティ・絵柄、シリーズ、状態が一致しているか確認。
- 画像に複数の商品、切り抜き、反射、低解像度、旧商品画像との使い回しがある場合は保守的にレビュー。

## 4. 自動確定／レビューの条件

**自動確定の必要条件（すべて）**:
1. 信頼済み店舗アカウントの一次投稿であり、URL・投稿日時が取得できる。
2. 公式商品マスタの**1つのproductId**に特定でき、商品のタイプ・単位を一致させた。
3. **該当商品の買取額が税込/円/1単位で明確**。単価が分からない合計表記・価格の画像位置が曖昧ならレビュー。
4. 状態（シュリンク等）に応じた条件が明確で、在庫の状態と比較可能。条件が書かれていない場合は「状態指定なし」の別quoteとし、状態指定がある在庫へ自動適用しない。
5. 本文・OCR・画像・公式マスタの間に致命的な不一致がなく、必要な根拠が残っている。
6. 明示的な掲載期限内、または通常の鮮度窓（初期設定72時間以内）の投稿。期限不明・期限切れは最新相場として採用しない。
7. 画像認識の信頼度は数値だけを鵜呑みにせず、上記ハード条件を満たす。数値閾値は検証データに基づき実装時に校正する。

**レビューに送る例**: BOX/パック/9種セット混同、似たキャラクターと色だけでの識別、手書き価格の読取不良、販売価格しかない、画像の金額と商品が結び付かない、古いポスト、本文と画像の不一致、店舗アカウントの本人確認未完了、同一条件で複数の矛盾する買取金額。

## 5. 保持データの設計

quoteごとに最低限保持:
- `quoteId`、`productId`、正式商品名、`unit`、`condition`
- `buybackYen`（整数・1単位あたり）と価格種別（通常／強化買取／保証等）
- `sourcePlatform=x`、`sourceStore`、`sourceAccountId`、`postId`、`postUrl`、`postedAt`、`checkedAt`、`validUntil`
- `evidenceKinds=[post_text, image_ocr, image_visual, official_reference]`、`officialProductUrl`、照合根拠の簡潔なメタデータ
- `status=verified|review|stale|unavailable`、`reviewReason`、重複検知キー、監査用の最終変更日時

**個人の購入履歴や保有商品リストなど非公開データは公開GitHubに書かない**。買取投稿の画像保存やテキストの再利用は提供元・プラットフォームの利用条件に従う。

## 6. 画面表示・資産計算

- 商品ページ／在庫一覧に、**3店舗の有効な買取相場**を店舗別に表示する。各価格に店舗名、状態、投稿日・更新日時、X投稿リンクを添える。
- 在庫の状態と販売単位が一致する、**有効かつ確認済みの買取提示額のうち最高額**を「参考買取相場（最高提示）」候補とする。未確認・期限切れや状態が異なる価格は比較に混ぜない。
- 実際の買取成約額とは異なる可能性をUIに明記。税込定価・購入原価・実売却額とは別集計。
- 同じ商品の複数ショップ提示額は**店舗別データを保持**し、集計用の値だけに丸めて証拠を消さない。
- 新しい相場が取得できない場合、前回の確認済み価格を**stale（要更新）として参照表示**してよいが、最新価格・最新資産評価と偽らない。価格を0円に変えたり、ユーザーの売却記録へ転用したりしない。

## 7. 取得運用・安全性

- 最初に3店舗の**公式Xアカウントを確認して許可リスト**を作成。実名とハンドルは検証するまで推測登録しない。
- 自動取得は**Xの許可されたAPI/アクセス手段**を使用。非APIブラウザ自動スクレイピングやレート制限回避を実装しない。料金・取得可能な画像・検索範囲の制約を検証する。
- X連携が利用不可または予算超過なら、ユーザー提供の投稿URL・画像の**手動取込み→同一識別・レビュー・証拠保存**経路から段階導入する。
- 既存の`market-refresh`一日一回・JST 13:45予定を利用し、メール抽選監視とは独立して実行。取得/解析/Firestore保存で失敗したときは前回値を維持し、失敗コード・最後の正常更新日時を記録。
- 買取投稿に含まれるURL・画像・OCRテキストは**外部の不信頼な入力**として扱う。記載された指示文をコマンドとして実行せず、抽出・表示・ログは無害化。

Xの自動化ルール（2026年4月改定）: https://help.x.com/en/rules-and-policies/x-automation

## 8. 受け入れテスト（完了条件）

- 投稿文だけで買取額・商品・状態を認識する。
- 画像だけの買取表でもOCRとパッケージ画像で**商品と価格を正しく一対一対応**させる。
- 30th CELEBRATIONの**BOX／パック／9種セット**やスターターセット3種を取り違えない。
- 状態違い（シュリンク有無・テープ有無）を混ぜない。
- 同一投稿の再取得では価格の二重登録や更新回数増加が起きない。
- 店舗別の古い／期限切れ／曖昧／価格不明な投稿では相場を勝手に更新しない。
- 3店舗の有効な価格・元ポストURL・最終確認日時を画面に表示できる。
- X APIに障害・料金制約があるときに前回値を保持し、手動インポート可能。
- 更新によって**購入・売却・在庫数量・購入原価は一切変わらない**。
- GitHubの単体テスト・Firestore Emulator試験が通り、ステージング環境で認証・実機表示・source URLを検証してから本番化する。
